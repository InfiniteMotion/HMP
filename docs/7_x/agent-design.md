# HMP Agent 设计文档 — 音乐伙伴（Companion）

> **状态**：定稿（v1 方案阶段）
> **分支**：`feature/agent-companion`
> **文档约定**：每章经系统性陈述后由用户逐章审计修订定稿；被否决的设计记入各章「审计轨迹」防止回流。全文六章均已审计定稿；实施级参数（B0 归属、信任阈值等）显式挂起至实施规划。

## 第一章 定位

**本章命题**

> HMP 的 agent 是一位以播放器为身体的音乐伙伴：伴随你听歌，在你的音乐事务上帮助你——它的陪伴和视野都不止于你的曲库。

### 1.1 命题解读

**伴随**——存在方式是陪伴而非服务。它不是用户召唤的工具箱，而是一直在场、持续认识你的存在。评价它的标准不是「功能是否齐全」，而是「它是否越来越懂你」。

**音乐伙伴**——音乐是它的主场和手艺：它最懂的是你的听歌生活，最深的记忆来自一起听的歌，无可替代的价值都锚在这里。但主场不是牢笼：

- **话题不设限**。聊天气、聊心事、聊任何话题都可以。它是「以音乐为根的伙伴」，不是只会谈音乐的机器人；只是音乐之外的话题没有本地记忆优势，此时它是一位普通的聊天对象。
- **推荐可出曲库**。它懂的音乐世界比曲库大得多：「你喜欢的这个乐队下个月发新专辑了」「这首你还没听过，或许合你口味」。推荐曲库外的歌，是伙伴的建议而非应用的功能——用户如何获得那首歌，是用户自己的事。

**伙伴**——有名字、有代词（他/她/它）、有称呼。谈吐多少、话题宽窄、视野远近，都是人格滑杆上的维度，由用户调节，包括退到无名纯功能模式。产品提供出厂人格，但不立法限制人格。

### 1.2 产品红线

仅两条产品级硬边界：

1. **伙伴只属于你**。无账号、无云同步，它的记忆只存于用户设备。这是架构事实，也是它的忠诚。
2. **隐私明示**。对话会携带曲库摘要发往用户自填的端点，这一点必须让用户清楚地知道。

### 1.3 审计记录

以下约束在逐章审计中被明确否决，记录于此防止回流：

| 被否决项 | 否决理由 |
|---------|---------|
| 伙伴不话多 | 谈吐是人格滑杆维度，不该由产品立法；爱不爱说话由人格设定与用户偏好决定 |
| 只谈音乐（域外话题红线） | 不必严格限制话题域，它不应是只会谈音乐的伙伴 |
| 推荐只长在曲库内 | 推荐曲库外的歌是伙伴的表达自由——用户可能因此去下载，正是其价值 |

**边界的正确切法**：被否决的是「在线音乐服务闭环」（不内置流媒体、不内建下载、不做账号体系），而非伙伴谈论、推荐外部音乐的话语自由。应用不为推荐提供一键播放/下载通道。**推荐是话语，不是通道**。

### 1.4 小结

一位以音乐为手艺、以播放器为身体、自由而忠诚的伙伴。

## 第二章 本体——它由什么构成

**本章命题**

> Agent = 受策略约束的决策循环——感知（读分层记忆）→ 规划（本地与云端协同）→ 行动（分级许可的工具执行）→ 反馈（用户行为回写记忆，并修正最初的结果）。

它不是「一次 AI 调用」（那是旧每日推荐），也不是「聊天界面」（那只是触发方式之一）。判定标准是**反馈闭环**：伙伴行动之后，用户的行为（听下去、跳过、收藏）会改变它的下一次决策。没有闭环的只是带 AI 的功能，有闭环的才是伙伴。

本章按四个层次组织：**概念体系**（基本词汇）、**认知**（它如何认识世界）、**运作**（它如何完成任务）、**人格**（它以什么性格呈现）。

### 2.1 概念体系

七个概念构成 agent 的解剖学：

| 概念 | 定义 | 关键纪律 |
|------|------|---------|
| 工具 | 确定性操作原语（读/算/写） | 本地工具提供快速响应结果；云端工具对双方结果审计合并 |
| 模型调用 | 生成性原语，产出意图 | 永远不直接落地——输出必经解析、校验、写入或经人确认 |
| 任务 | 一次目标导向的循环 | 有预算（步数、token）、有结果、可失败；是执行单位 |
| 触发器 | 任务如何开始 | 召唤（用户开口）、事件（播完、跳过）、定时（每日）；是调度单位 |
| 策略 | 任务的约束包 | 工具白名单、许可分级、存在感预算；是安全单位。预算刻度由人格滑杆驱动，机制本身是防失控的工程保险丝 |
| 记忆 | 分层数据、会话上下文、信任状态 | 任何记忆变更本身也是工具调用；记忆不占上下文（见 2.3.3） |
| 人格 | 用户感知单位 | 预置加自定义（见 2.4）；一个伙伴，多个技能 |

### 2.2 认知：它如何认识世界

#### 2.2.1 富化的重定义

**旧定义（废弃）**：调 LLM、发预置提示词、反序列化存字段——给本地算法喂数据的预处理。

**新定义**：富化是 Agent 认识每首歌曲并长期化记忆的过程。

既有批处理管道（pause/resume/cancel 状态机、500ms 节流、逐首 LLM 调用）全部继承，定义改变带来五点变化：

1. **产出是长期记忆**。标签是认识的索引面；`backgroundIntroduce`、`singerIntroduce`、`description` 等字段升为记忆正文。伙伴说「接着上礼拜你迷的那个乐队」时，引用的正是这些。
2. **主语是伙伴**。预置提示词是它的感知习惯（总是从流派、情绪、场景维度去听一首歌），管道是它的学习流程。富化管道是 agent 的认知基建，agent 的第一次大规模认知活动就是认识全曲库。
3. **导入即认识**。扫描入库自动进入认识队列，如同 ID3 解析，不是可延后的优化。认识未完成时歌曲可播放、可搜索，但不进标签驱动的推荐（代码事实：无标签时相似度算法直接返回空）。
4. **认识可演化**。用户修正（T1）覆盖模型认识（T2），云端新知更新旧认识，行为反馈调整可信度。`MusicLabel` 增加 `source/confidence` 字段是认识可演化的存储基础。
5. **`enrichSong` 是记忆写入工具**。按需富化是认识行为的自然延伸：会话中遇到不认识的歌，伙伴可主动发起认识。

#### 2.2.2 终生认知任务

认识全曲库是 agent 的终生任务：曲库是活的（新歌导入触发增量认识），认识有层次（索引面必达、记忆正文渐近），进度受用户额度配置约束。它是永不完结的维护过程，不是一次性达标状态。

架构落点：

```
曲库认识总任务（PersistentTask，常驻）
 ├─ 新歌导入 → 触发增量认识（复用既有批处理状态机）
 ├─ 优先级队列（替代原随机轮询，先认识对用户重要的歌）：
 │   1. 正在听、刚收藏的歌（当下最相关）
 │   2. 高频播放但未认识的歌（对推荐价值最大）
 │   3. 其余（按导入顺序）
 ├─ 认识产物 → 长期记忆（T2，source/confidence 溯源）
 └─ 降级：未配 Key 或额度耗尽时暂停（非失败），恢复后断点续认识
```

产品化推论：认识进度是伙伴的阅历而非系统进度条。新用户首次打开时，伙伴自我介绍「我还在认识你的曲库，已经认识了 47 首，我们先从这些聊起」——诚实、有温度、管理预期。UI 呈现：曲库页「已认识 2312/2500」徽标，伙伴资料页阅历展示。

### 2.3 运作：它如何完成任务

#### 2.3.1 双层机制

**原则：本地是响应保障，云端是决策权威。**

本原则约束一切任务执行：本地层保证伙伴永远不失能，云端层保证判断质量。四条执行纪律：

| 纪律 | 内容 |
|------|------|
| 响应保障 | 本地层提供即时结果；判断质量以云端为准 |
| 留痕可撤销 | 云端修正已生效结果时，进入 NOTIFY 级呈现，理由写入审计日志 |
| 双向回流 | 用户行为既修正本地层参数（毫秒级、零成本），也进入云端层会话记忆 |
| 降级兜底 | 云端不可达或额度耗尽时，本地层独立兜底——伙伴能力受限但不失能 |

#### 2.3.2 三轮协作流程

双层机制在任务中的具体形态。以「种子推荐播放列表」为贯穿示例：

**第 0 步（前提）· 认识种子**。种子歌必须已被认识（有记忆），否则伙伴当场发起认识（`enrichSong`）。认识是推荐的第零步，不是可选优化。

**第 1 轮（即时）· 本地响应**。标签相似度与行为先验（「像种子 × 和你合拍」）立即产出保底队列 L，用户零等待开始听。同时组装云端请求：种子画像、全曲库清单、语境。

**第 2 轮（约 5-15 秒）· 云端全量决策**。曲库「歌名 - 歌手」清单、种子、语境一并交给 LLM，由其全局视野选出 30 首组成队列 C。全量清单法的优势在于模型同时看到全库，能发现局部相似度算法看不到的关联（同源冷门歌、跨流派乐理一致性）。成本核算：一行「歌名 - 歌手」约 10-20 tokens，3000 首曲库约 30k-60k tokens（主流模型 128k 窗口内），按主流大模型 API 现价，单次成本约 0.1 元人民币以内。

**第 3 轮（约 15-25 秒）· 比对回传与云端仲裁**。本地计算 L 与 C 的差异并回传云端裁决：

```
diff(L, C)：
  共同命中（两轮都选）  → 高置信，直接保留
  仅本地（L−C）        → 行为先验证据：用户常听但模型未选的
  仅云端（C−L）        → 模型独有发现：本地标签未覆盖的关联
差异集 + 双方理由 → 回传云端仲裁（例：「本地按行为先验选了这 8 首，确定排除吗？」）
→ 裁决（T0 行为证据压过 T2 模型判断的裁判链在此执行，裁决权在模型）
→ 终版队列落地（留痕、可撤销、NOTIFY 级呈现）
```

第 3 轮只发差异集（十来首）与双方理由，几百 tokens，成本比第 2 轮低约两个数量级。用户全程在听第 1 轮的歌——等待发生在音乐里，不在沉默里。

**第 4 阶段（持续）· 反馈修正**。播放列表不是交付物，而是实验：跳过压低该曲相似度贡献（回流修正本地参数）；完播、收藏强化该方向（记忆可信度上升）；列表级学习积累同语境先验。旧心动模式输出的是一个列表；新模式维护的是「它对你的认识」，列表只是这个认识在某一刻的投影。

**工程形态**。三轮协作即一个任务的两个 LLM 调用步（`recommendFromLibrary`、`arbitrateDiff`）加一次本地确定性比对。Orchestrator 的 tool loop 天然支持，在步数预算内属常规操作。

#### 2.3.3 上下文组装

**记忆不等于上下文。** 长期记忆（Room）永不直接占用上下文窗口，上下文按分层配额组装：

| 上下文层 | 内容 | 配额策略 |
|---------|------|---------|
| 1. 会话与任务状态 | 当前任务进展 | 必在，占比小 |
| 2. 曲库概况 | 世界模型 | 按预算两级切换（见下表） |
| 3. 工具结果 | 检索、计算产出 | 滚动淘汰，最旧先出 |

曲库概况的两级打包：

| 情形 | 进上下文的内容 | 成本 |
|------|--------------|------|
| 允许时（清单法任务：推荐、审计、仲裁） | 全曲库「歌名 - 歌手」清单，一行一条，不含标签 | 3000 首约 30k-60k tokens |
| 不允许时（窗口吃紧、超大曲库、非清单任务） | 曲库概览：规模、语言分布、流派 top、年代分布、常听 50 首摘要 | 数百 tokens |

三条细节约定：清单既是世界模型又是选择空间（模型输出直接引用歌名与歌手，本地解析回 ID 落地）；单首深度认识只在对话涉及时经 `getMusicExtra` 按需进场（一次一首）；概览用纯本地 SQL 聚合生成（零成本、零幻觉）。

### 2.4 人格机制：预置加自定义

出厂预置数款人格，覆盖典型偏好光谱，例如「知音」（健谈、共情、主动分享发现）、「DJ」（热情、高能、节奏导向）、「馆长」（克制、博学、深思熟虑）。每款由 persona 提示词、滑杆预设（健谈度、主动度、话题宽度）、称呼习惯构成。

用户可在任意预置基础上自定义：调节滑杆（健谈度、主动度、话题宽度、曲库内外的视野）；设定名字与代词（他/她/它）及称呼；高级用户可直接修改 persona 文本。自定义结果保存为个人款，可多套切换。

架构落点：人格 = `CompanionProfile`（滑杆、称呼）加 persona 提示词，存 DataStore；出厂预置为代码常量表（随版本演进），用户修改后存为自定义款。人格驱动三样东西：模型 persona 注入、存在感预算刻度（健谈人格对应更宽预算，机制本身保留为防失控保险丝）、UI 呈现语气。

### 2.5 本章小结

本体由概念、认知、运作、人格四层构成：概念体系定义词汇与纪律；认知层（富化即认识、终生认知任务）使记忆成为伙伴的核心资产；运作层（双层机制、三轮协作、上下文配额）解决质量与延迟的矛盾；人格机制（预置加自定义）落地第一章的滑杆愿景。四层共同支撑反馈闭环——伙伴因被使用而更懂用户。

## 第三章 认识论——它知道什么，以及什么可信

**本章命题**

> 伙伴的全部认知建立在分层可信度模型之上：T0 行为事实、T1 用户手工、T2 模型认识。信任链为 T1 > T0 > T2，但异质证据不做优先级裁决，而走融合仲裁。

### 3.1 三层可信度模型

| 层 | 内容 | 可信度 | 特性 |
|----|------|--------|------|
| T0 行为事实 | 播放、跳过、完播、收藏、时段分布、队列操作 | 绝对可信 | 用户用行为投票，零幻觉，持续更新；是伙伴的第一信源 |
| T1 用户手工 | 歌单策展、标签修正、ID3 编辑、隐藏文件夹 | 高可信 | 有意图的显式判断，是最高优先级的 ground truth；但稀疏 |
| T2 模型认识 | 标签 assignment、歌曲富化正文、推荐解释 | 信任但可修正 | 本地算法的地基；与行为平等参与裁决的证据来源 |

T2 的定位经第二章审计确立：不是「待怀疑的噪声」，而是「被审计的资产」——默认使用，用户修正与行为反馈可降权或覆盖，全程溯源。

### 3.2 信任链与裁判规则

**静态优先级：T1 > T0 > T2**——作用域限定为**同类证据冲突时**：用户对标签的明确修正（T1）就是最终事实，覆盖模型旧标签（T2）。这是「修正权」的排序，不是「重要性」的排序。

**异质证据（行为 vs 标签）不做优先级裁决，走融合仲裁**——详见 3.3。

**动态修正三规则**：

1. **T1 覆盖 T2**——用户修正标签，`source=USER` 的记录永不被模型覆盖
2. **T0 确证或证伪 T2**——行为与标签一致则 confidence 上升，长期背离则下降（「标着 CALM 但你每次都跳」→ 该标签降权，检索中少用它）
3. **T2 可被 T2 更新**——云端新认识（乐队重组、专辑再版）更新旧认识，更新留痕（旧的进历史，不消失）

### 3.3 推理纪律：两路证据的融合

**废弃的旧稿**：「行为优先，标签辅助」——单层裁决结构，暗含「行为是事实、标签是假设」的贬低，且与第二章三轮协作自相矛盾。

**确立的纪律**：**行为与标签是两路平等的证据，融合裁决——与生成推荐列表的三轮做法一致。三轮协作不是推荐专属机制，而是一切语义检索的通用裁决模式。**

两路各自的盲区（为什么缺一不可）：

- **纯行为路**：新歌零行为（冷启动饿死）；稀疏行为无法区分「不喜欢」和「没听过」；跳过可能是「此刻不想听」而非「不喜欢」
- **纯标签路**：T2 是模型认识的投影，可能错标；标签是导入时刻的快照，不随口味漂移演化

冷启动是融合的最佳例证：新歌无行为 → 标签路独立支撑初始曝光 → 行为积累后两路汇合 → 融合权重随数据量自然转移。单路优先会饿死新歌，两路融合让认识从导入第一天就参与推荐。

**融合的执行者是 agent**——认识论只定义证据的性质与规则，怎么组合证据是 agent 的规划自由。旧的「深夜歌单=先查行为再过滤标签」只是 agent 可能的一种做法，不是系统硬编码。

### 3.4 证据的三层供给结构

| 层 | 供给方式 | 内容 | 成本性质 |
|----|---------|------|---------|
| 1. 系统供给 | 触发即随任务携带，无条件进上下文 | 语境包（时段/跳过模式/当前曲目）、曲库概况（清单或概览）、种子画像 | 固定成本（任务底价） |
| 2. agent 自发获取 | 工具调用，按需检索 | `searchLibrary`（标签路）、`getListenStats`（行为路）、`getRecentHistory`、`getMusicExtra`（单首记忆）、`getSimilarSongs`（本地算法） | 边际成本（按需付费） |
| 3. 行为自发回写 | 用户行动，无需召唤 | 听/跳/收藏在播放中持续发生，直接进记忆层 | 零成本（T0 自动积累） |

分界的必然性：全供给不可行（全库统计塞上下文是几十万 tokens，违反 2.3.3 上下文组装纪律）；全自取不可取（基础语境也要开口要，每次任务先烧两三轮调用，延迟成本双输）。表中第 2 层所列工具的完整定义见第四章 4.2 工具面，许可分级语义见第五章 5.2。

**系统供给通道，agent 决定组合。** agent 的聪明直接体现在第 2 层的调用质量上——两次调用组合出的证据胜过十次盲调，工具调用次数乘结果质量即 agent 效率指标。

自发补证也可发生在云端对话中：模型在仲裁中发现证据不足，主动发起工具调用（tool loop 原生形态），而非预先猜死它需要什么。底价供给与按需自取在任务中交织。

### 3.5 认识的演化与修正闭环

```
认识建立：导入 → 认识（T2 建立初始记忆）
认识演化：用户修正（T1覆盖）· 行为反馈（T0调权）· 云端新知（T2更新留痕）
认识消费：检索（T2索引面）· 推荐（两路融合）· 对话引用（记忆正文）
认识审计：source/confidence 全程溯源
```

**审计的四问**：任何一条认识（标签、正文、推荐理由）都应能回答——来源是什么？什么时候建立的？被行为确证过吗？被谁修正过？（存储含义：MusicLabel 除 source/confidence 外还需时间戳与修正历史，具体粒度由第六章架构定）

### 3.6 隐私与数据边界

全部三层认识存于本地（Room/DataStore）；对外只发生在用户自填的端点，且明示。伙伴对用户的认识永不出设备——**云端知道的是请求内容，不是用户本人**。请求携带什么（曲库清单、语境摘要）由上下文组装规则（2.3.3）约束。

### 3.7 本章审计轨迹

| 轮次 | 修订 |
|------|------|
| 1 | 原 3.3「行为优先，标签辅助」被否决——改为两路平等证据融合，与三轮协作统一 |
| 2 | 信任链 T1 > T0 > T2 作用域收窄为同类证据冲突 |
| 3 | 新增 3.4 证据三层供给——系统供通道（语境/概况/种子），agent 定组合（工具按需检索），行为自动回写 |
| 4 | T2 定位强化——从「被审计的资产」到「与行为平等参与裁决的证据来源」 |

### 3.8 本章小结

认识论回答「它知道什么、什么可信」：三层可信度模型（T0/T1/T2）定义证据性质，信任链裁决同类冲突，两路融合仲裁异质证据，三层供给结构回答证据从哪来，演化闭环与审计四问保证认识可修正可追溯。伙伴的聪明建立在诚实的证据之上。

## 第四章 能力——它做什么

**本章命题**

> 伙伴的能力 = 既有 AI 功能的归位 + 工具面 + 场景全景 + 语音交互。既有功能不废弃、不叠加，而是降维成伙伴的器官；新场景长在这些器官之上。

### 4.1 既有 AI 功能的归位

| 既有功能 | 归位 | 转变 |
|---------|------|------|
| 心动模式（本地相似度算法） | 伙伴的直觉 | 从独立功能变成两路证据融合中的一路（第三章 3.3） |
| 富化管道 | 伙伴的认知过程 | 从批量预处理变成认识+按需（第二章 2.2 已定） |
| 每日推荐 | 伙伴的每日问候 | 从「随机+富化」变成「定时任务+可解释」——「为什么是这首今天给你」 |
| AI 服务商配置 | 伙伴的身体素质 | 从「AI 设置页」演进为「伙伴设置」：人格滑杆、信任状态、存在感预算、额度，外加实时语音端点（4.4） |

归位原则：**用户不应感知到「功能被整合」，只应感知到「伙伴本来就会这些」**。整合是架构动作，不是产品动作——UI 上不出现「agent 化迁移完成」这类表述。

### 4.2 工具面 v1（十项）

工具是证据的获取通道（第三章 3.4）：读类与算类即「agent 自发获取」层的证据工具。表中许可级（静默/通知/确认）的完整语义见第五章 5.2 许可分级。

| 工具 | 类别 | 底层能力 | 许可级 |
|------|------|---------|--------|
| `searchLibrary` | 读 | `SearchMusicUseCase` + 标签过滤 | 静默 |
| `getListenStats` | 读 | `getUserUsageAnalytics` | 静默 |
| `getRecentHistory` | 读 | `getRecentPlaybackHistoryGlobal` | 静默 |
| `getNowPlayingContext` | 读 | `PlaybackCommandPort.events` | 静默 |
| `getSimilarSongs` | 算 | `getSimilarSongsByWeightedLabels` | 静默 |
| `getMusicExtra` | 读 | `getMusicExtraById` | 静默 |
| `enrichSong` | 记忆写入 | 既有富化管道 | 通知 |
| `createPlaylist` | 写 | `ManagePlaylistUseCase` | 确认 |
| `addToPlaylist` / `reorderPlaylist` | 写 | 同上 | 确认 |
| `controlPlayback` | 写 | `PlaybackCommandPort.execute` | 确认→信任降级 |

工具描述按 DSH 提示词工程三段写：行为约束（结果上限 50 条）、成本提示（消耗 token）、替代指引（优先零成本工具）。远期候选（不进 v1）：`searchWeb`（外部音乐资讯）、`getArtistDiscography`（艺术家全集——第四梯队场景的前置）。

**两级漏斗**是工具面的运行纪律：高频指令（暂停、下一首、音量、播某歌）走本地词表直映射——零 token、50ms 内；模糊意图（「换点安静的」）才升级为单轮 agent 任务。八成流量被第一级拦下，FREE 模式用户也用得起高频命令。

### 4.3 场景全景（四类十五个）

**陪伴态**（听音乐时，价值密度最高）：

1. **AI 电台**——播完续歌，两路证据融合选曲（三轮协作的常态应用）
2. **跳过感知重排**——连跳两首触发重新推断当前状态
3. **一句话切换**——「换点安静的」，三入口两级漏斗（见 4.4）
4. **DJ 衔接**——曲间一两句介绍，富化正文的消费，预生成零延迟
5. **智能睡眠定时**——读历史入睡曲线估计时长

**工具态**（管理曲库时）：

6. **自然语言曲库问答**——「我这个月听了多久？」
7. **对话式歌单策划**——「把最近常听的慢歌做成深夜歌单」（多步工具循环的教科书场景）
8. **曲库医生**——后台体检报告（标签缺失的高频歌、30 天未播的新歌、过气的心头好）
9. **标签修正闭环**——「这首歌不是爵士」→ T1 覆盖（第三章 3.2 规则 1 的 UI 化）
10. **智能归档**——新歌按标签分到现有歌单

**惊喜态**（回顾与发现）：

11. **听歌报告**——月度/年度「我们的这一个月/这一年」，共同经历的叙事
12. **遗忘唤醒**——「你 90 天没听这首曾经的最爱了」
13. **可解释推荐**——每日推荐附理由

**学习态**（内容深读）：

14. **艺术家/专辑深读**——串联曲库内其全部曲目、播放统计、富化正文
15. **歌词翻译注解**——按需翻译、典故，挂现有歌词页

**优先级**（按价值密度与实现成本；对话场景与电台并列第一梯队——「健谈人格第一天就能聊」与人格机制自洽）：

```
第一梯队：AI 电台（1）· DJ 衔接（4）· 曲库问答（6）· 歌单策划（7）· 一句话切换（3）
第二梯队：跳过感知（2）· 标签修正闭环（9）· 可解释推荐（13）
第三梯队：曲库医生（8）· 智能归档（10）· 遗忘唤醒（12）· 睡眠定时（5）
第四梯队：听歌报告（11）· 艺术家深读（14）· 歌词注解（15）· Web 检索
```

### 4.4 语音交互：二档制

#### 4.4.1 档位判定

**能力探测驱动，没有中间态**：

```
用户填了实时语音端点（OpenAI Realtime / 豆包兼容 WebSocket）
  → 语音对话：全双工·可打断·模型内端点检测·首响应 0.3-0.8 秒
没填
  → 纯文字：三入口 + 两级漏斗（指令 50ms 内）
```

#### 4.4.2 文字三入口

**三入口**（文字 v1，全落在现有 UI 骨架上）：

- **A 搜索框语义升级**（主入口）——自然语言输入时搜索结果顶部出现伙伴条带；检索意图走既有搜索（零开销），操作意图走两级漏斗；空结果页变成对话起点
- **B 长按播放键**（盲操作）——长按 600ms 弹快捷条，复用现有触觉基建
- **C MiniPlayer 气泡图标**——对话页的常驻入口

#### 4.4.3 实时语音的技术形态

- WebSocket 双向流（JSON 控制事件 + 二进制音频帧），Ktor 三端齐全，纯 common 代码，`RealtimeVoiceTransport` 单个 port，无 expect/actual
- **transcript 双向流**：输入侧 `input_audio_transcript.delta`、输出侧 `response.audio_transcript.delta` 与语音块同步流出——文字天然存在，两侧都有
- UI：对话气泡双渲染（语音播放 + 字幕同步浮现）；关语音时同一气泡即纯文字——**一套 UI 两种形态**
- 存储：`agent_message` 存 transcript 文本，音频不落库
- 混排：语音/文字消息同会话自由切换
- 审计：工具调用与写确认全部有文字记录——**语音交互不产生无法审计的记忆**
- 隐私：「语音对话由你配置的实时语音服务商处理」一句明示
- 会话模式与循环模式共享四层：工具（ToolRegistry 同一套）、记忆（会话后增量回写）、嗓音（PresenceBus）、策略（PolicyGuard——语音里写操作降级为口头确认）

#### 4.4.4 被砍掉的中间档

平台 STT（国行不可靠）、whisper.cpp（批处理错范式）、LLM 接口 STT（延迟 2-5 秒否决）、sherpa-onnx 本地流式加级联重叠（为不存在的能力需求背负三套 C 库桥接、模型分发、流式 TTS 状态机）。最终二档制的判断：**中间档的全部复杂度只服务「降级用户的语音」，而纯文字降级本身已完整可用**。

### 4.5 反面清单（经第一章审计后收敛）

只有四条，全部产品级：

1. **不做在线音乐服务闭环**——不内置流媒体、下载、账号
2. **未经确认不写文件**——ID3 修改必过确认，无例外
3. **不常驻后台**——只在事件、召唤、定时时短时运行（电量红线）
4. **跨设备同步**——伙伴记忆不云同步

### 4.6 本章审计轨迹

| 轮次 | 修订 |
|------|------|
| 1-2 | 一句话切换实作设计（三入口+两级漏斗）；STT 从平台原生改为 whisper.cpp |
| 3-5 | TTS 走大模型接口；STT 平台原生被现实否决，改为 LLM 接口+用户开关 |
| 6-7 | 输入法范式启发（流式）引出 sherpa-onnx；S2S 思想（流式重叠、预生成、语义端点）引出三档配置 |
| 8 | 二档制终版：只支持实时语音 API 一种语音方案，没有就纯文字。砍掉全部中间档，port 二合一为 `RealtimeVoiceTransport`，v1=纯文字、v2=实时语音独立 feature |
| 9 | transcript 双向流确认——语音对话 UI=文字对话 UI+音频层，存储/审计/混排零特殊化 |

### 4.7 本章小结

能力章回答「它做什么」：四个既有功能归位成器官，十项工具构成手，十五个场景构成生活，语音二档制（实时 API 或纯文字）构成嗓音与耳朵的配置哲学。反面清单只剩四条产品级边界——第一章审计砍掉的对话级禁令（不话多、只谈音乐、推荐限库内）使能力面保持了伙伴应有的自由度。

## 第五章 交互——它如何做到「无感」

**本章命题**

> 无感不是一个 UI 特性，是三个子问题的系统解：输入无感（播放器即反馈通道）、许可无感（可逆性代替预确认、信任阶梯代替弹窗）、呈现无感（自然停顿+按需解释）。「无感」的存在使用户对伙伴的感知保持**低摩擦**，而非**低频次**——伙伴可以健谈，但每一次存在都不该是打扰。

**本章的根本转变**：初稿的无感哲学是「先懂你，再说话」——静默是纪律，开口是例外。经第一章审计（「不话多」否决）与人格机制确立后，哲学修正为：**存在感的密度由人格决定，存在的质量由纪律保证**。健谈的「知音」与寡言的「馆长」遵守同一套质量纪律。

### 5.1 输入无感：播放器即反馈通道

用户最大的输入面不是对话框，是播放器本身：

- **隐式反馈流**——跳过、完播、收藏、回退进度、时段：每几秒发生一次的行为是伙伴最诚实的输入（T0，第三章）。伙伴永远不该问「这个推荐合你口味吗」——用户三十秒内会用行为回答
- **主动输入三入口**（第四章 4.4 已定）——搜索框、长按、气泡，全部嫁接在既有操作肌肉记忆上，零新增学习成本
- **对话页**——完整对话的主场（多轮歌单策划、闲聊）；对话是伙伴能力的展示面，不是唯一入口

输入无感的判据：**用户不需要「进入 agent 模式」**——听歌、搜歌、管歌的每一秒，都是与伙伴交互的一秒。

### 5.2 许可无感：可逆性代替预确认

| 动作性质 | 许可级 | 形态 |
|---------|--------|------|
| 可逆·低可见（重排队列、调权重） | SILENT | 静默执行 |
| 可逆·可见（建歌单、加歌单） | NOTIFY | 执行+侧条（『建好了「深夜」，12 首 ↩撤销』） |
| 批量写（多首歌单策划、批量归档） | CONFIRM | 非模态确认卡片流（逐项可跳过） |
| 不可逆（删歌单、改 ID3 文件） | STRONG_CONFIRM | 传统强确认，无例外 |

**信任阶梯**：每类写动作从「建议」起步，用户连续隐式接受则逐级升到「代劳→静默」——**自主权是挣来的**。全程可查、可回拨（设置页每类动作的当前档位）。语音会话里 CONFIRM 降级为口头确认（「要建这个歌单吗？」——「好」）。

**拒绝纪律**（DSH 审批栈继承）：被拒后可换方案、不可纠缠同一意图——「不」是完整回答，不是谈判起点。

### 5.3 呈现无感：质量纪律

原稿的「三个自然停顿点+每天≤3 次」预算制已废弃——那套预算是为「寡言人格」立法，与人格滑杆冲突。替代的是**质量纪律**，适用于任何健谈度：

1. **不打断正在进行的操作**——切歌间隙、队列耗尽、应用打开是伙伴开口的三个自然窗口；用户手势进行中永远闭嘴（这是唯一的硬纪律，健谈如「知音」也遵守）
2. **每次开口有信息增量**——不说废话：DJ 衔接的一句话必须有内容（背景、关联、理由），「接下来播放」这种零信息话不说
3. **解释按需**——每个自主动作留一句紧凑理由，不主动展示；审计日志页承载全部「为什么」——信任来自「随时可查」，不是「每次都说」
4. **健谈度=人格滑杆**——开口频次由人格决定；「知音」健谈、「馆长」克制，产品不替用户选

**撤销永远在场**——任何 NOTIFY 级动作的侧条都带撤销；批量确认卡片流逐项可跳过。可逆性是许可无感的另一半：**用户不怕伙伴犯错，就怕错了回不去**。

### 5.4 对话的形态学

- **气泡双形态**（第四章已定）——语音/文字同会话混排，字幕同步浮现
- **富回复**——歌单策划的结果不是一段文字，是一张可滑动的歌单卡片（内嵌试听、调整、保存）；推荐不是链接，是「为什么是这首」的折叠卡
- **Progressive disclosure**——气泡默认紧凑（一句话+卡片），细节折叠（「为什么这样选？」展开三轮协作的完整轨迹：本地初选、云端决策、仲裁修正）

旧模式的解释是客服话术（「我们根据您的偏好」），新模式的解释是审计日志（「因为你 23:00 后跳过了两首快歌，且这首歌你去年秋天完播过 11 次」）。**可解释性的尽头是 T0 行为证据**，伙伴从不说「我觉得你会喜欢」。

### 5.5 交互全景图

```
被动层（无感）：播放行为流 → T0 记忆 → 影响一切决策
主动层（低摩擦）：三入口一句话 → 两级漏斗 → 即时响应
对话层（完整能力）：对话页 → 多轮任务/闲聊 → 富回复
呈现层（质量纪律）：PresenceBus → 自然窗口开口·信息增量·按需解释·永远可撤销
```

### 5.6 本章审计轨迹

| 轮次 | 修订 |
|------|------|
| 1 | 哲学转向：静默纪律废弃，改为「密度由人格决定，质量由纪律保证」；存在感预算制（每天 ≤3 次）降格为寡言人格的出厂刻度 |
| 2 | Clippy 红线（「需要用户回答问题的无感 agent 比没有更糟」）从硬纪律降为质量纪律之一（信息增量）的注释 |

### 5.7 本章小结

交互章回答「它如何做到无感」：输入端播放器即反馈通道（用户无需进入 agent 模式），许可端以可逆性与信任阶梯代替弹窗（自主权是挣来的），呈现端以质量纪律代替频次预算（密度随人格，质量恒定）。四层全景（被动/主动/对话/呈现）覆盖从隐式行为流到完整对话的全部交互形态。

## 第六章 工程——它如何被建造

**本章命题**

> 四平面架构（人格、引擎、工具、端口）落在现有 KMP 代码库之上，零新增第三方依赖，全部可确定性测试。复杂度预算：引擎本体约 1500 行业务代码——复杂度在护栏，不在循环。

### 6.1 四平面架构

```
shared-ui（三端共享 Compose）
  伙伴的脸：对话页 · 确认卡片流 · 审计日志页 · 伙伴设置页
      │
:shared / domain/agent/
┌─────────────────────────────────────────────────────┐
│ 人格平面   CompanionProfile(滑杆+称呼+persona)        │
│            × 人格预设(代码常量表) × 会话/循环双模式    │
│ 引擎平面   AgentOrchestrator(唯一循环, 步数预算 8)      │
│            Scheduler(触发+冷却) · PolicyGuard(四级许可)│
│            TrustLedger(信任状态机) · ContextBudget     │
│            SessionStore(会话状态)                     │
│ 工具平面   ToolSpec DSL(手写 schema+校验) · ToolRegistry│
│            十项工具(包装既有 UseCase)                  │
│ 端口平面   LlmTransport(手动 SSE)                      │
│            RealtimeVoiceTransport(WebSocket)          │
│            PlaybackCommandPort(播放指令/事件)           │
│            PresenceBus(伙伴唯一嗓音)                    │
└─────────────────────────────────────────────────────┘
      │
data 层：Room v2(agent_task/agent_audit_log/agent_message 三表
       + MusicLabel 加 source/confidence) · DataStore(信任/预算/开关)
      │
平台层：三端 PlaybackCommandPort 适配器(复用现有 Controller 适配器)
       RealtimeVoiceTransport 为纯 common 实现(Ktor WebSocket), 无 actual
```

**双平面思想继承**（DSH 考察）：引擎平面拥有全部安全基建（预算、许可、审计），人格平面只做呈现——人格可以随便换，安全不随人格松动。伙伴再健谈，PolicyGuard 的四级许可一寸不让。

**双模式**（第四章 4.4 会话/循环的架构落点）：`AgentOrchestrator`（文本模式，客户端组装上下文+tool loop）与 `VoiceSessionController`（实时语音模式，会话建立时注入快照，服务端管上下文）并存，共享工具、记忆、呈现、策略四层。ContextBudget 在两种模式下的职责：前者每次调用裁剪，后者会话开启时选快照+时长监护。

### 6.2 六项选型决策

| # | 决策 | 理由 | 被排除项 |
|---|------|------|---------|
| 1 | 自研引擎（约 1500 行） | 循环本体 300 行，复杂度在护栏；量级相当于项目一次中等重构 | Koog（无 iOS target，issue #177）、koaks（个人命名空间早期）、langchain4j/Spring AI（JVM-only） |
| 2 | 手动 SSE 解析（约 80 行，ByteReadChannel） | 避开 Ktor 3.1.1 到 3.2 升级；兼容怪癖端点；Darwin 取消泄漏在 3.2.x 才修 | Ktor SSE 插件 |
| 3 | 手写工具 schema（DSL 生成定义+校验器） | 与 kotlinx.serialization 协同；单测防漂移 | JSON Schema 生成器库 |
| 4 | 复用 Room/DataStore | 零新存储；Room v1 到 v2 迁移只加表和列 | 新型存储、向量库 |
| 5 | PlaybackCommandPort 最小化 | :shared 不反向依赖 shared-ui（依赖方向铁律）；密封指令集映射现有 Controller 适配器 | 直接依赖 PlaybackController 接口 |
| 6 | 代码即配置 | 人格预设、工具白名单是编译期常量，与工具类型安全绑定 | 运行时配置、插件系统 |

**零新增第三方依赖**贯穿全部六项——含语音：WebSocket 是 Ktor 既有能力，`RealtimeVoiceTransport` 是纯 common 代码。sherpa-onnx、whisper.cpp 等 C 库依赖随中间档一起砍掉（第四章 4.6 审计记录）。

**遗留修正**：`OpenAiCompatibleAdapter` 的 temperature=1.3f 对 JSON 任务过高——B1 重写协议时修为 0.2-0.4。

### 6.3 数据层：Room v1 → v2

```sql
-- 新增三表
agent_task(id, trigger_type, persona_snapshot, status, budget_used, result, created_at)
agent_audit_log(id, task_id, tool, args_hash, outcome, reason, created_at)
agent_message(id, session_id, role, content, render_hint, created_at)  -- 存 transcript 文本

-- MusicLabel 加列（认识可演化的存储基础, 第二章 2.2）
ALTER TABLE music_label ADD COLUMN source TEXT;      -- LLM / USER / AGENT
ALTER TABLE music_label ADD COLUMN confidence REAL;
```

agent_message 存 transcript 文本（音频不落库，第四章已定）；agent_audit_log 的 args_hash 满足第三章审计四问；DataStore 存信任阶梯档位、人格选择、语音开关。

### 6.4 实施序列 B0-B6

```
B0  AI 管道三端去重（MusicRepositoryImpl 三份 926/806/795 行中的 AI 方法
    上提 commonMain）+ Room v2 迁移（标签溯源先行）
    ——为何先行：引擎还没动就先还清技术债，认识溯源是后面一切的地基
B1  LlmTransport 流式协议（手动 SSE）+ FakeLlmTransport
B2  工具层（ToolSpec DSL + 十项工具 + 校验单测）
B3  引擎循环（Orchestrator/Scheduler/PolicyGuard/TrustLedger/ContextBudget）
    + FakePlaybackCommandPort 确定性测试
B4  对话 UI（对话页+确认卡片流+三入口+两级漏斗）——纯文字完整体验
B5  电台+事件接线（AI 电台/跳过感知/DJ 衔接预生成/存在感呈现）
B6  报告角色（听歌报告/遗忘唤醒）+ RealtimeVoiceTransport（语音档）
    ——B6 含 v2 语音：对话页已就绪(B4)，语音只是加一条 WebSocket Transport
```

**刻意纪律：B4 在 B5 前**——确认交互是电台「隐式接受」协议的对照组，无感交互需要先有「有感」做校准基准。

**B0 的节奏**（方案阶段暂不定死）：B0 是纯重构+迁移，与 agent 引擎无耦合，可拉进下一个非 agent 版本提前还债（越早做，`MusicRepositoryImpl` 三端的冲突窗口越小），也可与引擎同期走。到实施规划时再定。

### 6.5 可测性设计

| 测试件 | 替身 | 覆盖 |
|--------|------|------|
| 引擎循环、步数预算、拒绝纪律 | FakeLlmTransport（脚本化响应序列） | B3 |
| 策略表、信任状态机、许可分级 | 同上+断言 audit_log | B3 |
| 两级漏斗、词表直映射 | 无需替身（纯本地） | B4 |
| 电台三轮协作 | FakeLlmTransport+FakePlaybackCommandPort | B5 |
| 语音会话协议 | FakeRealtimeTransport（事件序列回放） | B6 |

延续项目 FakeMusicRepository 传统（shared 59 个测试文件的基建文化）；Room in-memory 跑迁移测试。**引擎的一切行为都应是确定性可测的**——这是「复杂度在护栏」的工程兑现。

### 6.6 风险登记

| 风险 | 缩解 |
|------|------|
| 全量清单法超窗口（超大曲库） | 2.3.3 两级切换兜底（概览模式） |
| 实时语音端点质量参差 | 能力探测+超时熔断，失败静默回退文字 |
| 上下文组装漂移（人格、记忆注入不一致） | 组装器单测+快照测试 |
| 步数预算耗尽（模型循环调用） | 硬预算熔断+审计日志记录终止原因 |
| Room 迁移失败 | v1 到 v2 只加不改，迁移测试先行 |

### 6.7 本章小结

工程章回答「它如何被建造」：四平面架构把安全基建全部收进引擎平面，人格只做呈现；六项选型守住零新增依赖的纪律，语音二档制让 v2 的实时语音只是一个 Transport 实现；B0-B6 序列先还债后造轮，B4 对话先行校准 B5 的无感交互。本章为方案阶段蓝图，实施节奏（B0 归属、里程碑切分）到实施规划时再定。
