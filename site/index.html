设计理念

好的音乐播放器应该尊重用户，而非绑架用户

☁️

不做云同步

数据存储在设备本地。无需网络即可使用全部功能，地铁、飞行模式不受影响。

👤

不引入账号系统

无需注册登录，打开即用。无账号泄露风险，隐私始终属于你。

💬

不做社交功能

不添加好友、不分享动态、不做社区。专注音乐播放，回归工具本质。

🔒

不收集用户数据

无埋点、无分析、无遥测。你的听歌记录和偏好完全私密，零数据收集。

核心原则

纯本地优先 — 数据完全由用户掌控，备份还原均在本地完成。AI 推荐是唯一的网络功能，且需用户自行配置 API Key。

架构演进

三次重大架构变迁，每一次都在前一步基础上渐进演进，从不推倒重来

阶段一 · v1.0 – v4.0

单体架构

从零搭建基础播放功能，所有代码集中在一个模块。快速验证产品方向，积累核心能力。

基础播放播放列表搜索与歌词
阶段二 · v5.0 – v5.9

模块化架构

拆分为 5 个独立模块，引入 Hilt + Media3。AI 多服务商、动态主题、毛玻璃、Navigation 3 等核心特性集中落地。

5 模块拆分Media3AI 推荐动态主题Navigation 3
阶段三 · v5.10+

跨平台架构

KMP Monorepo，共享 domain + data 层。新增 iOS 与 Desktop 双平台。平台原生 UI，各取所长。

KMPRoom KMPKtorKoiniOSDesktop

关键技术决策

每个选择背后都有明确的原因和权衡

2025.11

模块化重构

从单体拆分为 5 模块，引入 Hilt + Media3

代码量增长导致维护困难，需要清晰的模块边界和职责分离

2025.12

多 AI 服务商

支持 5 家而非绑定单一提供商

避免供应商锁定，给用户更多选择，降低单点故障风险

2026.04

Navigation 3 迁移

从字符串路由迁移到类型安全导航

编译时类型检查，消除路由拼写错误，支持深度链接

2026.05

KMP 跨平台

共享业务逻辑，UI 保持平台原生

业务逻辑复用减少重复，原生 UI 保证各平台最佳体验

2026.05

Room KMP vs SQLDelight

排查后选择修复 Room 而非迁移

问题根因是 Gradle 配置，修复成本远低于全量迁移
